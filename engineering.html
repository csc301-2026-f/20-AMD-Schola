Tests that are hard to fool

About 10,900 lines of test code sit beside 11,300 lines of plugin code.

Without the engine

128 core cases cover spaces, the lifecycle, the connector loop and stackers. 35 inference cases run real ONNX models. 22 transport cases run a full gRPC session, including oversized payloads, timeouts, a Python hang-up and a port that's already taken.

Inside Godot

206 GdUnit4 tests load real scenes headlessly. The training host has the largest suite, with 43 tests of its own.

Against Python

Five test models come from Schola's own Python exporter, with the actions ONNX Runtime returned in Python recorded beside them. Godot has to reproduce those exact actions.

No silent passes

The D3 smoke suite fails unless every group of checks finishes, and the exported app must also print a completion marker, so a script that crashes but still exits cleanly can't pass.

From half an hour to minutes

Early CI rebuilt gRPC from source, which took over 30 minutes, and spent about 8 minutes on godot-cpp. We cached compiled objects across runs and committed prebuilt gRPC packages, each with a record of exactly how it was built. By our before-and-after comparison that cut build time by 93%, and the TA picked it out at the D3 demo.

A manual workflow can still rebuild gRPC from the pinned source when a version changes. Its output goes up for review rather than being committed automatically.

Every dependency, pinned and checked

One lockfile pins each dependency to an exact version, commit or hash, and CI fails if a submodule drifts from it.

When the downloads went away

On November 17 we lost access to ONNX Runtime's upstream downloads. Within a day the build installed offline from packages repacked out of Microsoft's signed NuGet release: both signatures verified, and all 69 payload entries byte-identical to the signed originals.

The written record also says what those checks don't prove. We'd rather be precise than reassuring.

Everywhere else

GitHub Actions are pinned to full commit hashes, build tools install with hash checking, and every Godot editor, export template and test framework download is checked against a SHA-256 before use.

Releases on a schedule

Course snapshots are automated so nobody has to be awake at the deadline. D2 was published from a tag. D3 was tagged on main at the deadline by a scheduled workflow, and the tag then triggered the build that published the three desktop packages.

D4 is scheduled the same way for November 27 at 11:30 p.m. Toronto time. The workflow refuses to run from any branch but main, checks that the tag points at the commit it packaged, and on a retry only uploads what's missing.

How changes land

Small, described pull requests

Changes are squash-merged with Conventional Commit titles. The template asks for a summary, the related story and how it was tested.

A development contract

Shared infrastructure such as the build, CI, entry points and pins changes only in its own focused pull request, so feature work never quietly changes everyone's build.

A formatting hook that checks what you commit

The optional pre-commit hook checks the staged snapshot, not the working copy, so a tidy editor buffer can't hide badly formatted staged code.

Next upThe full test suites run on Linux; Windows CI currently checks dependencies and linking. AMD asked for test runs on Windows too, and that is on our list.
