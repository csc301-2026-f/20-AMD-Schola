Contracts first, then code.

We split the port into user stories, had AMD approve each set, and merged every story's API before its implementation. That let seven people build spaces, lifecycle, transport, configuration and inference at the same time.

How we planned

Each story names its user, its acceptance criteria, what is out of scope, and how it was verified.

  1. DraftThe first story set was drafted on September 29 from the MVP AMD set at kickoff: define an environment, train it with Schola's Python tools, export to ONNX, run it in Godot.
  2. ApproveAMD approved the set on October 2. A separate export-validation story was folded away, since Schola's Python side already exports models, leaving US1 to US5 and US7.
  3. Agree the APIsBetween October 9 and 15 every owner merged an API-only pull request. Interfaces and abstract types meant dependent stories could start before anything was implemented.
  4. BuildOwners worked on named branches, sometimes in pairs, and landed focused pull requests with a testing section and a required CI check.
  5. IntegrateAfter D2 we merged shared dependencies before the code that used them and tested against one runnable example.
  6. Second waveOn November 6 AMD approved US8 to US14, split into MVP and stretch goals. US15 came out of the same meeting.

Every story, and where it stands

Status is checked against the history of main as of November 22, 2026, not against plans. Ten stories are merged, one is partly merged and three are on branches heading for D4.

Feedback that reshaped the stories

We met AMD every Friday. These are the discussions that changed code, not just plans.

  • Four separate step callbacks are ambiguous. AMD, October 23; decided October 30

    Reward, termination, truncation and info now come back together from one _get_step_result(agent) (US5).

  • A built-in step limit will fight custom truncation logic. AMD, October 23 and 30

    We removed it and the planned step-limit node. Developers return truncated: true when their own rule says so (US4, US5).

  • Delaying actions and rewards harms learning. AMD, October 23

    The non-blocking poll was dropped. The connector blocks once per physics frame, so each action and its reward land on the same frame (US3).

  • Can the recurrent sequence length come from the model? Our question, October 23; approved as US14 on November 6

    ONNX Runtime's C API couldn't read the metadata where it lived, so AMD changed Schola's exporter upstream and we removed the manual setting entirely. Unreal still sets it by hand.

  • Make stackers generic observation adapters. AMD, November 6

    ScholaStacker is the first implementation of an abstract ScholaObservationAdapter that agents apply in order (US10).

  • Inspector bounds get tedious for big spaces. AMD, November 6

    Became US15, an optional callback that defines spaces in code.

  • Avoid warning soup. AMD, November 6

    Environments now show one warning summary per agent instead of repeating every problem.

Saying no on purpose

An idea only becomes a story if it passes all five of these:

  • It solves a concrete problem a Godot developer has.
  • Schola's behaviour stays the same across engines.
  • It can't be done as a task inside an existing story.
  • AMD accepts the cost of maintaining it.
  • It doesn't delay the end-to-end train, export and run workflow.

That rule is why Unreal-only systems such as StateTree and imitation learning are deliberately not being ported, and why parallel training inside one Godot process stays a possible follow-up rather than a story.
