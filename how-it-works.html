How it works

The plugin is a C++17 GDExtension for Godot 4.7. This page covers how it's put together, what happens during training and inference, and how we test it.

The layers

All the reinforcement learning logic lives in a core written in plain C++. It doesn't include any Godot, gRPC, Protocol Buffers or ONNX Runtime headers, which is a rule in our development contract. Each of the other layers connects that core to one technology.

Because the core never touches the engine, about 3,000 lines of it are covered by 128 Catch2 unit tests that run in seconds without starting Godot.

The plugin ships as two libraries. schola has the nodes, spaces, sensors, actuators, training host and ONNX inference, and it's what an exported game includes. schola_training has the gRPC server and the connector node. It creates the training host by class name and talks to it through ordinary Godot method calls, so it never links against the runtime's C++. Leaving training out of an export is one filter: addons/schola_training/*.

What happens in one step

The order is fixed, so results are reproducible and a bad action can't leave the world half-updated.

  1. Every action is checked against its agent's action space. Missing or extra actions are rejected before anything moves.
  2. _act(action) runs for every active agent.
  3. _observe() and then _get_step_result(agent) run for each agent, in scene-tree order. Agents that joined during the step get their first observation here.
  4. Agents that left during the step are turned into terminal transitions.
  5. episode_ended fires once every agent has finished.

Training

Godot speaks the same wire protocol as Unreal, so Schola's existing Python client can drive it without changes.

The connector waits once per physics frame for Python's next request, so an action and its reward always land on the same frame. A few Unreal conventions carry over as well: port 8000 by default, a -ScholaPort override, and a 45-second start timeout that matches Python's. Messages can be up to 100 MB each way, which leaves room for camera observations.

The Godot side is merged and tested over a real network connection against a C++ client that speaks the protocol. A full training run with Schola's own Python trainer is the part we're still verifying for D4.

Running a trained policy

In a shipped game there's no Python. On each physics frame:

  1. The agent's _observe(), or its sensors, produce an observation.
  2. Any observation adapters, such as a stacker, run in order.
  3. ScholaOnnxPolicy runs the model with that agent's own policy state.
  4. The action is checked against the action space and applied.

The policy holds no per-agent data, so one loaded model can drive many agents. Recurrent models pair their state_in and state_out tensors, read their sequence length from the model's metadata, and only keep new state once inference succeeds. Inference runs on the CPU, on the main thread.

Testing

There's about as much test code as plugin code: roughly 10,900 lines against 11,300.

SuiteTestsWhat it covers
Core (Catch2)128Spaces, the lifecycle, the connector loop and stackers, without the engine.

Every pull request that touches Godot code, the shared protocol or the workflows runs the jobs below. They all report into one required check, which also passes for docs-only changes and fails if change detection itself breaks.

Early on, CI rebuilt gRPC from source, which took over 30 minutes, and spent about 8 minutes on godot-cpp. Caching compiled objects and committing prebuilt gRPC packages cut build time by 93% in our before-and-after comparison.

The full test suites only run on Linux so far. Windows CI checks dependencies and linking, and AMD has asked us to run tests on Windows too.

Dependencies

One lockfile pins every dependency to an exact version, commit or hash, and CI fails if a submodule drifts from it. gRPC and Protocol Buffers are pinned to the same versions Unreal Schola uses, pending AMD's sign-off.

On November 17 we lost access to ONNX Runtime's upstream downloads. Within a day the build installed offline from packages repacked out of Microsoft's signed NuGet release, with both signatures verified and all 69 payload entries byte-identical to the signed originals. The write-up in the repo also lists what those checks don't prove.

Elsewhere, GitHub Actions are pinned to full commit hashes, build tools install with hash checking, and every Godot editor, export template and test framework download is checked against a SHA-256 first.

Releases

Decisions

C++ instead of C#

C# would have limited the plugin to Godot's .NET build. A C++ GDExtension works in every build and gave us ONNX Runtime's C API directly. We looked at Rust too, and ruled it out over licensing concerns with the option we evaluated.

One shared protocol

Godot generates its gRPC code from the repository's Proto/ directory, and our contract forbids a Godot-only copy, so the two engines can't drift apart.

One type for every space

AMD suggested we look at templated spaces. We kept a single variant type, which keeps validation, conversion and the Godot resources in one place, and walked AMD through the trade-off at the next meeting.

No nested environments

An environment inside another one has no clear meaning for training, so it's rejected with an Inspector warning and a clear error. We wrote it up as a decision record.
