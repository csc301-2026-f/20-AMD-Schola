# US14: Read the state sequence length from the model

- **Owner:** Unassigned
- **Status:** Approved; implementation progress not yet reported
- **Priority:** Stretch goal
- **Last updated:** Nov. 6, 2026

## Story

As a Godot developer, I want a recurrent policy to take its state sequence length from the exported model so that I do not have to remember the training value and cannot get wrong actions from a mismatched setting.

## Rationale

Schola's exporter records `has_seq_dim`, `max_seq_len`, and `seq_dim` on each state input. `ScholaOnnxPolicy` currently ignores that metadata and uses `max_state_sequence_length`, which the developer sets by hand and which defaults to one. A wrong value produces wrong actions with no error. Unreal's `MaxStateSequenceLength` is also set by hand, so the outcome should be agreed with AMD to keep the engines consistent.

ONNX Runtime's C API exposes model-level custom metadata but not the metadata on individual inputs, so the exported value cannot currently be read through ONNX Runtime.

## Acceptance criteria

- A model that declares `max_seq_len` for a state input runs with that length without any manual setting.
- Invalid metadata, such as a non-integer or a value below one, produces a clear error when the policy initializes.
- Exported games gain no training or transport dependency, and the runtime add-on stays separate from the training add-on.
- Tests cover each case above and include a recurrent model with a sequence dimension exported by a real Schola trainer.
- The inference guide documents where the length comes from and when the manual setting applies.

## Scope limits

- Work starts once Alex's ONNX metadata-export PR lands, as agreed at the [Nov. 6 partner meeting](../../../deliverables/team/minutes/partner-meeting-07.md). That PR is a prerequisite for this story.
- This story does not change how state history is stored or updated.
- It does not change Unreal Schola or the shared exporter until AMD adds changes.
