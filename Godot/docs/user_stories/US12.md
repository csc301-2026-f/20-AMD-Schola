# US12: Train multiple agents simultaneously

- **Owner:** Sanjay
- **Status:** Implemented and tested in Godot; `schola rllib train` run on Windows or Linux pending
- **Priority:** MVP (highest priority)
- **Last updated:** Nov. 19, 2026

## Story

As an ML practitioner, I want to train multiple agents in one environment so that I can build cooperative and competitive reinforcement-learning scenarios.

## Rationale

Simultaneous multi-agent training is an expected outcome of the Godot port. The existing Schola protocol already represents agents independently, so Godot should prove that its environment, lifecycle, and transport layers preserve agent identity and correctly route each action and result.

## Acceptance criteria

- Validate the existing Godot multi-agent components through real training; the Nov. 6 meeting identified this proof as the remaining focus.
- One environment can expose two or more agents to Python.
- Agents may declare different observation and action spaces where the existing Schola protocol supports them.
- Agent identifiers and their ordering remain stable for the lifetime of a training session.
- Actions, observations, rewards, termination, truncation, and info are routed to the correct agent.
- Cooperative agents may share rewards, while competitive agents may receive different rewards.
- Per-agent and environment-wide episode-completion behavior is documented and matches the existing Schola protocol.
- A supported Python trainer completes multiple episodes with at least two simultaneous agents.
- Tests cover duplicate IDs, missing or extra actions, different spaces, agent-specific results, resets, and session failure.
- The implementation does not introduce Godot-only multi-agent semantics.

## Progress

Godot already represented agents independently: the environment adapter (US1) collects every `ScholaAgent`, rejects duplicate IDs, and has all agents act before any is observed, and the lifecycle (US4) keeps one result per agent and checks each step's actions. US12 proves this with a two-agent scene, Godot tests, and Schola's Python client.

- **Two-agent example.** [`examples/multi_agent/`](../../examples/multi_agent/README.md) trains two agents on a number line in one environment. `runner` observes `Box(2)` and acts with `Discrete(3)`; `hopper` observes `Discrete(10)` and acts with `MultiDiscrete([2, 2])`, two buttons that are each 0 or 1. It used `MultiBinary(2)` at first, but RLlib has no action distribution for `MultiBinary` and stopped before training. `reward_mode` switches between individual and shared rewards. Each agent terminates at the goal or is truncated at `max_steps`, so agents finish on different steps, and each result's `info` names its agent.
- **Reconnecting after Python closes a session.** `schola rllib train` connects once to read the agents, closes, and connects again to train. `ScholaTrainingConnector` used to stop after the first session. It now waits for Python's next session on the same port, as Unreal Schola does, with a fresh internal `ScholaTrainingHost` each time; the closing host releases its environments so the next one can initialize them. The Python side is unchanged. Details are in the [Godot README](../../README.md#train-with-python).
- **Tests.**
  - `tests/integration/multi_agent_training_test.gd` (9 tests) drives the example through the real `HostTrainingBackend` and `ScholaTrainingHost` with `ScholaTrainingTestClient`, which now returns each agent's `info`. It covers the definition of both agents and their spaces; each agent's own observation, reward, flags, and info from one step; shared rewards; an agent finishing early, which stops acting while its final result is repeated; truncation at the step limit; stable IDs and order over three episodes; a missing action and an action for a finished agent, each rejected before anyone moves and ending the session; and an agent freed mid-session.
  - `tests/integration/training_connector_test.gd` checks that a fresh host can train the same two agents after the previous session closes. It fails without the environment release.
  - Duplicate agent IDs are covered by `training_host_test.gd`, and missing, unknown, and finished-agent actions by the lifecycle unit tests.
- **Python check (macOS, not committed).** Against the running example, Schola's unmodified RLlib environment classes read both agents and their spaces in a discovery session, then completed 5 episodes with random actions in a second session. Agents finished on different steps, and every result's `info` named the right agent. Godot reported `session_closed` twice and then `training_finished("")`.
- **Pending.** Run `schola rllib train ppo --timesteps 4000 editor --port 8000` against the example on Windows or Linux, following its README, and record the completed episodes here. Schola's Python CLI does not start on macOS: `schola/core/utils/ubt.py` rejects the platform on import.

### Acceptance criteria status

| Criterion | Evidence |

The merged gRPC tests in [PR #47](https://github.com/csc301-2026-f/20-AMD-Schola/pull/47) also route actions and rewards across two environments with two agents each, using a C++ client. ## Scope limits

- This story validates the multi-agent behavior already represented by Schola; it does not add a new matchmaking, team, or league-training system.
- Dynamic addition or removal of agents during an active training session is excluded unless AMD approves corresponding protocol semantics.
