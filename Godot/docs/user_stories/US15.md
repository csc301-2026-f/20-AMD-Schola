# US15: Define observation and action spaces in code

- **Owner:** Vansh
- **Status:** Implemented and locally tested in PR #58; review and merge conflicts pending
- **Last updated:** Nov. 21, 2026

## Story

As a Godot developer, I want to define observation and action spaces in code so that I can configure large, repeated, or nested spaces without manually editing many Inspector fields.

## Rationale

Inspector configuration works well for simple spaces but becomes cumbersome for complex definitions. Programmatic construction supports loops, reusable helpers, and parameterized subspaces. Coding assistants can help author and maintain these definitions and their sanity and round-trip tests.

Existing Box resources already broadcast a single low or high bound across an explicit shape. This story builds on that behavior and the existing space resources rather than introducing different space semantics. Unreal Schola's definition callbacks provide design evidence for the code-based workflow.

## Acceptance criteria

- A script attached to `ScholaAgent` can implement an optional `_define_spaces()` callback that supplies both observation and action spaces, including through an inherited implementation.
- Support existing Schola space types, including nested Dict spaces, without introducing different validation or serialization semantics.
- Provide convenient constructors for programmatic definitions, including Box spaces with explicit shapes and repeated bounds.
- Allow loops and reusable helper functions to construct repeated or parameterized subspaces.
- Preserve Inspector-based configuration when the callback is absent. Document that an implemented callback supplies both spaces and takes precedence over Inspector assignments; invalid callback results must not silently fall back to those assignments.
- Resolve and validate definitions before runtime configuration checks in both Python training and standalone ONNX inference.
- Report malformed callback results, missing spaces, and invalid definitions with actionable, agent-specific errors.
- Keep resolved definitions stable throughout a session; applying changed definitions requires reinitialization.
- Avoid executing the callback during ordinary Inspector warning checks. Recognize callback-based configuration without reporting unused empty Inspector fields as missing spaces.
- Tests cover Inspector fallback, callback precedence, nested and repeated spaces, invalid results, equivalent resource definitions, serialization round trips, and training/inference initialization.
- Include a current example and documentation showing a large Box observation, repeated nested spaces, and an action space.

## Callback and lifecycle contract

- `_define_spaces()` takes no arguments and returns a Dictionary containing `observation` and `action`, each a non-null `ScholaSpace` resource. The native binding uses `Variant` so malformed results can receive explicit validation errors.
- Definitions must be deterministic and use configuration available before session initialization. They must not depend on episode state or modify gameplay state.
- The first successful resolution captures a validated snapshot. Repeated `define()` calls, episode resets, policy-memory resets, and resource edits reuse that snapshot rather than rebuilding it.
- The initial supported rebuild boundary is to stop affected consumers, recreate the configured scene with new agent/environment instances, and initialize again. Reinitializing a policy alone does not clear the agent snapshot.
- Failed resolution publishes no snapshot and permits a corrected retry. Successful resolution remains cached if a later initialization stage fails.
- Inspector assignments remain saved as authored; callback resolution does not overwrite them. Discovering callback-defined spaces requires executing the callback on a configured instance, and its results do not automatically appear in the Inspector.

See the [space-definition API contract](https://github.com/csc301-2026-f/20-AMD-Schola/blob/32a1758ce2b21cf790996e781f35dcd5c2ce9b80/Godot/docs/us15_space_definition_api.md) for detailed behavior and implementation status.

## Scope limits

- Editor preview, generated `.tres` authoring workflows, automatic type generation, new space types, and camera capture are excluded.
- Resource save/load tests may use temporary files; that does not add resource generation as a user workflow.
- Live reconfiguration of active training or inference sessions is excluded.
- Examples and documentation belong in current Godot directories; frozen deliverables and demos remain unchanged.
