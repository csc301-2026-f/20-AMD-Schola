# US11: Observe the environment through a camera sensor

- **Owners:** Bohdan, Vansh
- **Status:** Camera sensors merged through US8; exported-policy fixture added; dedicated example and real-camera training/inference validation pending
- **Priority:** Stretch goal
- **Last updated:** Nov. 19, 2026

## Story

As a Godot developer, I want an agent to receive image observations from a camera sensor so that I can train and run vision-based policies.

## Rationale

Schola for Unreal provides a camera sensor that converts rendered output into normalized observations. Godot should provide the same capability through its camera, viewport, texture, and image APIs after US8 establishes the common sensor interface.

## Acceptance criteria

- A reusable camera sensor participates in the sensor composition model defined by US8.
- A developer can configure observation width, height, and supported color channels through the Inspector.
- The sensor declares a Box observation space whose shape, bounds, and data type match the produced image values.
- Captured pixels use a documented channel order, tensor layout, normalization range, and frame timing.
- The implementation validates incompatible camera, viewport, image-format, and channel configurations before training or inference begins.
- Camera observations work during both Python training and local ONNX inference.
- The sensor operates correctly in the supported headless training configuration or reports a clear unsupported-configuration error.
- Tests cover observation shape, channel selection, normalization, capture timing, and repeated captures.
- The documented observation semantics correspond to Unreal Schola's camera sensor wherever the engines provide equivalent rendering data.

## Progress

`ScholaCameraSensor` reads rendered color and normalized depth from Godot SubViewports. `ScholaFakeCameraSensor` provides deterministic CHW images without rendering. See [the component guide](../us8_components.md) for capture timing, configuration, layout and headless constraints. Native environment dispatch and real GPU color/depth capture are covered by `components_parity_test.gd` and `camera_render_test.gd`. Broader packaged-platform and renderer coverage remains follow-up work.

- The sensor implementation is already on main through US8 PR #51 (`d777891`);
  it does not need a separate camera-specific observation-space type. Images use
  an existing float32 Box in `[channels, height, width]` order with bounds `[0,1]`.
- Branch `Bohdan-Vansh/us11/camera-sensor` adds an **untrained** Schola-exported
  SB3 PPO fixture (`212dea34`) and a C++ ONNX inference comparison against Python
  ONNX Runtime reference outputs (`fc0a4c51`). These are compatibility checks,
  not evidence of learning or a real rendered-camera training session.
- Remaining work: a committed camera example, real rendered pixels driving the
  exported policy, a production Python training smoke test, and targeted
  configuration/timing coverage. Existing tests exercise real capture and fake
  camera inference separately; they do not prove that combined workflow.
- Rendering/connector scheduling is an open integration decision with US3.
  Startup, reset-image freshness, and rendering progress during blocking
  connector calls must be checked before claiming real-camera training support.

See the [US11 completion plan](../us11_implementation.md) for implementation
defaults, validation gates, and the scheduling experiment. This status update
records inspected code and committed tests; it is not a new test run.

## Godot interface

- The sensor is a scene-owned node because it participates in the scene tree and camera lifecycle.
- Rendering is implemented with Godot-native camera and viewport APIs rather than an Unreal-shaped abstraction.
- Configuration problems appear as Inspector warnings; runtime capture failures use the shared Godot error-handling rules.

## Scope limits

- US8's merged sensor composition contract is the baseline; reuse it.
- The first example will use RGB at 64x64 with a rotation action matching the
  current fixture. Existing depth/color-depth behavior remains supported and
  covered separately. Ordinary headless display mode remains unsupported for
  real readback; fake-camera tests are not real-camera training evidence.
- A production training smoke test should verify optimizer updates over multiple
  episodes. Reproducible learned-performance benchmarking remains US13's scope;
  any change to this completion boundary should be agreed with the story owners.
- Performance work is limited to producing camera observations reliably; asynchronous or pipelined inference is not part of this story.
- Normalized depth is supported through a dedicated viewport and the supplied linear-depth material. Segmentation and automatic scene mirroring are outside the current implementation.
