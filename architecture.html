Small core, two extensions.

The plugin is a C++17 GDExtension built in layers. All the reinforcement learning logic sits in a core that knows nothing about Godot, and Godot, gRPC and ONNX Runtime each live in their own module around it.

The layers

Every module depends inward on the core, never the other way round.

  • Your gameGDScript environments and agents, spaces set in the Inspector, four hooks.
  • bindingsThe Godot nodes and resources: ScholaEnvironment, ScholaAgent, the five space types, sensors, actuators and ScholaTrainingHost.
  • inferenceScholaOnnxPolicy and ScholaInferenceStepper, on the ONNX Runtime 1.30 C API.
  • transport, trainingThe gRPC server for Schola's GymService and the ScholaTrainingConnector node, in a separate extension.
  • interopConverts Godot values to and from core types. Compiled into both extensions.
  • corePlain C++17: spaces, environment interfaces, the lifecycle, the connector loop, stackers and the stepper. No Godot, gRPC, Protocol Buffers or ONNX Runtime headers.

Why it mattersBecause the core never touches the engine, about 3,000 lines of core logic, from the lifecycle and spaces to the connector, stackers and stepper, are covered by 128 Catch2 unit tests that run in seconds without starting Godot. The rule is written into our development contract.

Shipped games carry no networking stack

Training needs gRPC and Protocol Buffers. A finished game doesn't, so they live in a different library.

schola, the runtime

Seventeen classes: the scene nodes, spaces, sensors and actuators, the training host and ONNX inference. This is what an exported game ships, along with ONNX Runtime.

schola_training

The gRPC server and the connector node. It creates the runtime's training host by class name and talks to it only through Godot method calls, so it never links runtime C++ code. Exports drop it with one filter: addons/schola_training/*.

What happens in one step

The order is fixed so results are reproducible and a bad action can't leave the world half-changed.

  1. ValidateEvery action is checked against its agent's action space. Missing or extra actions are rejected before anything moves.
  2. Act_act(action) runs for every active agent.
  3. Observe and score_observe() then _get_step_result(agent) run per agent, in scene-tree order. Agents that joined mid-step get their first observation here.
  4. ReconcileAgents that left during the step become terminal transitions.
  5. Finishepisode_ended fires once every agent has terminated or been truncated.

When something fails

Every core call returns a status and leaves its outputs untouched on failure. A failed environment moves the session to a faulted state that only accepts close(), and errors reach Python as matching gRPC codes and developers as Godot errors that name the agent at fault.

The training path

Godot speaks the same wire protocol as Unreal, so Schola's existing Python client can drive it unchanged.

  1. PythonSchola's own client, from its SB3 or RLlib integrations, connects to the running scene.
  2. gRPCThe GymService code is generated from the repository's shared Proto/ files, the same ones Unreal and Python use.
  3. Hand-offgRPC worker threads only queue each request. The Godot main thread does all conversion and game work.
  4. SceneThe connector's training host resets and steps every ScholaEnvironment in the scene.

The connector blocks once per physics frame for Python's next request, so an action and its reward always land on the same frame. Small Unreal conventions carry over too: port 8000 by default, a -ScholaPort override, and a 45-second start timeout that matches Python's. Messages can be up to 100 MB each way, enough for camera observations.

The Godot side is merged and tested over a real network connection against a C++ client that speaks the protocol. A full training run with Schola's own Python trainer is the piece still being verified for D4.

The inference path

In a shipped game, Python is gone. Each physics frame:

  1. ObserveThe agent's _observe() or its sensors produce an observation.
  2. AdaptObservation adapters, such as a stacker, run in order.
  3. InferScholaOnnxPolicy runs the model with that agent's own policy state.
  4. ActThe action is checked against the action space and applied.

The policy holds no per-agent data, so one loaded model can drive many agents. Recurrent models pair state_in and state_out tensors, read their sequence length from the model's metadata, and only commit new state once inference succeeds. Inference runs on the CPU, on the main thread.

From Unreal to Godot

AMD asked for a Godot-native port, not a line-by-line translation. Concepts carry over; the APIs follow Godot's conventions.

Decisions we'd make again

C++ over C#

C# would have limited the plugin to Godot's .NET build. A C++ GDExtension works in every build and gave us ONNX Runtime's C API directly. Rust was ruled out over licensing concerns with the option we evaluated.

One shared protocol

Godot generates its gRPC code from the repository's Proto/ directory and our contract forbids a Godot-only copy, so the engines can't drift apart. gRPC and Protocol Buffers are pinned to the same versions as Unreal Schola.

One variant type for spaces

AMD suggested templated spaces. We kept a single variant type, which keeps validation, conversion and the Godot resources in one place, and we presented that trade-off at the following partner meeting.

No nested environments

Nesting one environment inside another has no clear meaning for training, so it is rejected with an Inspector warning and a clear error. It is written up as an accepted decision record.
